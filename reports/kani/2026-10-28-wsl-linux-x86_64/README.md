# Kani proofs: compiled models never panic

[中文](#中文)

**Claim.** For the two models that `examples/embedded-predict` compiles with `model!`
(`defects`, gradient-boosted trees, and `defects_mlp`, a 35-32-16-1 network), prediction
never panics, for every possible input: any number (NaN and infinities included), any
category, any missing value.

**How.** `predict` is `decode(&outputs(&features(input)?))`. Each stage is proved total
for every value of its argument's type, which is a superset of what the stage before it
can return. For the trees, `outputs` is proved one walk at a time: walking any tree with
any feature values stays inside the arrays and ends at a leaf. `outputs` adds one walk per
tree to each output's starting score. `value` has one entry per node, and the generated
code asserts at compile time that there is one starting score per output, so with every
walk in range the sum cannot panic either. The harnesses are generated by `model!`
itself (its `kani` option): `defects::proofs` and `defects_mlp::proofs` in
[`examples/embedded-predict/src/lib.rs`](../../../examples/embedded-predict/src/lib.rs),
with the loop bounds taken from each model's shape (the deepest tree, the widest layer,
the missing-value tokens). Nothing is written by hand, so every model compiled with the
option gets the same proofs.

**Where.** The development machine (AMD Ryzen 9 9950X3D2), WSL2 Ubuntu 26.04 (Linux
6.6.87.2). Kani 0.68.0 with CBMC 6.11.0 and its pinned toolchain nightly-2026-08-21.
The results are one plain `cargo kani`, the way CI runs it, on a fresh copy of the code of
the commit that brings this version of the report. Every process was limited to 14 GB of
address space (`ulimit -v`), because a GitHub-hosted Linux runner has 16 GB of memory.

## Settings

`examples/embedded-predict/Cargo.toml` sets `[package.metadata.kani.flags]
no-overflow-checks = true`, so a plain `cargo kani` uses it. What stays on:
- Rust's own checks, which are panics: arithmetic overflow (the crate is built with
  overflow checks), division by zero, shift overflow, and indexing;
- Kani's memory-safety checks;
- the unwinding checks, which prove that the loop bounds are large enough.

What is off: CBMC's additional checks for conversions and for floating-point NaN and
overflow. They are not about panics, and one of them is a false positive here (below).

| `defects_features_are_total` | 0 / 415 (8) | 11.3 s | 527 MB | SUCCESSFUL |
| `defects_tree_walk_is_total` | 0 / 130 | 11.4 s | 1,857 MB | SUCCESSFUL |
| `defects_decode_is_total` | 0 / 93 (17) | 0.4 s | 54 MB | SUCCESSFUL |
| `defects_mlp_features_are_total` | 0 / 415 (8) | 11.5 s | 530 MB | SUCCESSFUL |
| `defects_mlp_layers_are_total` | 0 / 187 (1) | 26.7 s | 1,478 MB | SUCCESSFUL |
| `defects_mlp_decode_is_total` | 0 / 93 (17) | 0.4 s | — | SUCCESSFUL |

The whole run took 72 s, compilation included. Memory was sampled once a second; the
network's decode proof ends before the first sample. The hand-written harnesses that
these replace had the same check counts (the generated loop bounds are the ones the
model needs: depth 8 + 2 for the walk, 32 + 2 for the layers, 2 + 2 for the tokens),
and ran in 69 s. The features proof of the network also passes with Kani's default
checks, which are stricter: 0 of 421 failed, in 20.0 s.

## Findings on the way

**Walking all the trees in one proof needs too much memory.** The first tree proof,
`tree_traversal_is_total`, ran `outputs` on any features: all 14 walks in one formula.
With Kani's default checks it passed on this machine, which has 63 GB of memory, in
412 s. Limited to 14 GB, the run stops 30 s in with "Solver ran out of memory during
propositional reduction", with either settings. In CI, the `kani` job stopped after about
3 minutes. Every array index in a walk depends on the comparisons
before it, so Kani can slice nothing away, and each step reads the node arrays of all 14
trees. One walk, through any tree, is 130 checks, 1.7 GB and 11 s. The earlier reruns of
the all-trees proof with the final settings were cut off when the WSL virtual machine
shut down, each time at that same step; it was most likely out of memory too.

**Proving the whole network did not finish.** An earlier single harness for the
network (`predict` on any input) was still solving after about 20 minutes. With the
default settings, `network_layers_are_total` was still running after 32 minutes when it
was cut off. With the default settings, CBMC's floating-point checks need the value of
every multiply-add in the layers. Without them, no check depends on the arithmetic,
and CBMC slices it away: 26 seconds.

**A false positive in CBMC's NaN check.** With the default settings,
`tree_decode_is_total` failed 1 of 113 checks: "NaN on division" in `libm`
0.2.16, `src/math/exp.rs` line 121. Concrete playback
(`cargo kani -Z concrete-playback --concrete-playback=print`) gives the input: a logit of
−∞. `sigmoid(−∞)` calls `exp(−∞)`. Its underflow branch evaluates
`force_eval!((-x1p_149 / x) as f32)` (−2⁻¹⁴⁹ / −∞) only to raise the underflow flag.
IEEE 754 defines a finite number divided by an infinity as 0, and `exp(−∞)` returns
0, so `sigmoid(−∞)` is 0. CBMC's NaN check treats any division by an infinity as a
possible NaN; only ∞/∞ and 0/0 are. Nothing panics on this path, and no NaN is produced.

## Reproduce

```sh
cargo install --locked kani-verifier   # Kani runs on Linux and macOS
cd examples/embedded-predict
cargo kani                              # all six; or --harness proofs::<name>
```

`bash tools/verify.sh --all` runs the same proofs together with every other check.

## 中文

**结论。** `examples/embedded-predict` 用 `model!` 编译了两个模型（梯度提升树 `defects` 和 35-32-16-1 的神经网络
`defects_mlp`）。对任何可能的输入（任何数值，包括 NaN 和无穷大；任何类别；任何缺失值），它们的预测都不会 panic。

**方法。** `predict` 就是 `decode(&outputs(&features(input)?))`。每一段都对其参数类型的所有取值证明是全函数，
而这个取值范围包含了前一段所有可能的输出。梯度提升树的 `outputs` 按单棵树证明：任意一棵树、任意特征值，都只在数组范围内走，
最后停在叶子上。`outputs` 把每棵树的叶子值加到各输出的初始分上；`value` 每个节点一项，生成的代码又在编译期断言每个输出正好有一个初始分，
所以只要每次遍历都不越界，求和也不会 panic。证明由 `model!` 自己生成（`kani` 选项），循环上界取自模型的形状，没有任何手写的部分。
6 个证明在一次普通的 `cargo kani` 里全部通过，跑法和 CI 相同，
每个进程限制 14 GB 地址空间（GitHub 的 Linux runner 有 16 GB 内存）。连编译共 72 秒，每个证明的 CBMC 内存都不到 2 GB。

**配置。** Rust 自己的检查全部保留：整数溢出、除以零、移位和数组越界都会 panic，Kani 也检查内存安全和循环展开。关掉的是 CBMC 额外的
浮点 NaN、溢出和类型转换检查：它们和 panic 无关，其中 NaN 检查在这里还是误报。CBMC 把“任何数除以无穷大”都当成可能产生 NaN，
因此在 `libm` 的 `exp(−∞)` 里报错；但按 IEEE 754，有限数除以无穷大等于 0，`exp(−∞)` 返回 0，这条路径既不会 panic，也不会产生 NaN。

**发现。** 最初的树证明 `tree_traversal_is_total` 把 14 棵树的遍历放进一个公式：在这台 63 GB 内存的机器上用默认配置跑了 412 秒才通过；
限制在 14 GB 时，30 秒就报内存不足；CI 的 kani 任务大约 3 分钟就中断了。遍历中每个数组下标都取决于前面的比较，
Kani 切不掉任何部分，而且每一步都要读全部 14 棵树的节点数组。改成任意一棵树的单次遍历后，只有 130 个检查，1.7 GB，11 秒。
之前用最终配置重跑它时，WSL 虚拟机几次关机，每次都停在同一步，多半也是内存耗尽。
把整个网络作为一个证明时，30 分钟内都没有解完；分段之后，没有任何检查依赖网络的浮点运算，CBMC 把它们切掉，网络层只用 26 秒。
