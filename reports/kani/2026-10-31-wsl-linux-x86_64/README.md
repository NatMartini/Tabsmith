# Kani proofs: compiled models never panic

[中文](#中文)

**Claim.** For the two models that `examples/embedded-predict` compiles with `model!`
(`defects`, gradient-boosted trees, and `defects_mlp`, a 35-32-16-1 network), prediction
never panics, for every possible input: any number (NaN and infinities included), any
category, any missing value. With the trees as generated code, Kani proves all 14 of them
in one proof, in 4.8 s and 104 MB. As arrays, that proof does not fit in 14 GB.

**How.** `predict` is `decode(&outputs(&features(input)?))`, and each stage is proved total
for every value of its argument's type, which is a superset of what the stage before it can
return. The harnesses are generated by `model!` itself (its `kani` option), with loop bounds
from each model's shape. Nothing is written by hand, so every model compiled with the option
gets the same proofs. The settings and the reasons for them have not changed since
[the report of 2026-10-28](../2026-10-28-wsl-linux-x86_64/): Rust's own checks and Kani's
memory-safety checks stay on, and CBMC's additional floating-point checks stay off, because
they are not about panics and one of them has a false positive.

**What changed.** `model!` now turns each tree into a function of nested `if`s
([reports/inference](../../inference/2026-10-31-windows-x86_64/)). In a walk over arrays,
every index depends on the comparisons before it, so Kani can slice nothing away. In
generated code every index is a constant, one the compiler has already checked, so no check
depends on any comparison.

**Where.** The development machine (AMD Ryzen 9 9950X3D2), WSL2 Ubuntu 26.04 (Linux
6.6.87.2). Kani 0.68.0 with CBMC 6.11.0 and its pinned toolchain nightly-2026-08-21. The
results are one plain `cargo kani`, the way CI runs it, on a fresh copy of the code of the
commit that brings this report. Every process was limited to 14 GB of address space
(`ulimit -v`), because a GitHub-hosted Linux runner has 16 GB of memory.

| `defects_outputs_are_total` | 0 / 3,390 | 4.8 s | 104 MB | SUCCESSFUL |
| `defects_decode_is_total` | 0 / 93 (17) | 0.3 s | – | SUCCESSFUL |
| `defects_mlp_features_are_total` | 0 / 415 (8) | 9.7 s | 546 MB | SUCCESSFUL |
| `defects_mlp_layers_are_total` | 0 / 187 (1) | 25.2 s | 1,471 MB | SUCCESSFUL |
| `defects_mlp_decode_is_total` | 0 / 93 (17) | 0.4 s | 61 MB | SUCCESSFUL |
| `defects_arrays_features_are_total` | 0 / 415 (8) | 9.3 s | 529 MB | SUCCESSFUL |
| `defects_arrays_tree_walk_is_total` | 0 / 130 | 10.2 s | 1,689 MB | SUCCESSFUL |
| `defects_arrays_decode_is_total` | 0 / 93 (17) | 0.3 s | – | SUCCESSFUL |

The whole run took 81 s, compilation included. Memory was sampled once a second, so a
dash means the proof ended before the first sample. `defects_arrays` holds the same trees
as `defects`, in the form a very large ensemble keeps (`tree_arrays`). It exists only under
`cfg(kani)`, so that this form stays proved; the firmware does not contain it.

## The same trees, in both forms

| Proof of the trees' `outputs` | Form | Time | Peak CBMC memory |
|---|---|---|---|
| One walk, through any tree (`defects_arrays_tree_walk_is_total`) | arrays | 10.2 s | 1,689 MB |
| All 14 walks in one proof ([earlier report](../2026-10-28-wsl-linux-x86_64/)) | arrays | out of memory at 14 GB; 412 s with 63 GB | more than 14 GB |
| All 14 trees in one proof (`defects_outputs_are_total`) | code | 4.8 s | 104 MB |

The arrays need one walk at a time, and an argument around it: `outputs` adds the walks' leaf
values, so it cannot panic once every walk stays in range. The generated proof runs `outputs`
itself. It is this easy because there is little left to prove: a program with constant
indices and no loops has nowhere to go out of bounds. That is the point of the form, and the
proof confirms it for the code that actually runs. It says nothing about the values; the
output bounds and `self_check` do.

`outputs_batch` is not part of `predict`, and these proofs do not cover it.

## Reproduce

```sh
cargo install --locked kani-verifier   # Kani runs on Linux and macOS
cd examples/embedded-predict
cargo kani                              # all nine; or --harness proofs::<name>
```

`bash tools/verify.sh --all` runs the same proofs together with every other check.
`summary.txt` is the summary of this run.

## 中文

**结论。** `examples/embedded-predict` 用 `model!` 编译了两个模型（梯度提升树 `defects` 和 35-32-16-1 的神经网络 `defects_mlp`）。
对任何可能的输入（任何数值，包括 NaN 和无穷大；任何类别；任何缺失值），它们的预测都不会 panic。树生成为代码后，Kani 能在一个证明里证明全部 14 棵树，
只用 4.8 秒和 104 MB。数组形式下，同样的证明在 14 GB 内放不下。

**方法。** `predict` 就是 `decode(&outputs(&features(input)?))`，每一段都对其参数类型的所有取值证明是全函数。证明由 `model!` 自己生成（`kani` 选项），循环上界取自模型的形状，没有任何手写的部分。
配置和 [2026-10-28 的报告](../2026-10-28-wsl-linux-x86_64/)相同：Rust 自己的检查和 Kani 的内存安全检查保留，CBMC 额外的浮点检查关闭，因为它们和 panic 无关，其中一个还有误报。

**变化。** `model!` 现在把每棵树生成为嵌套 `if` 的函数。遍历数组时，每个下标都取决于前面的比较，Kani 切不掉任何部分；生成代码里每个下标都是编译器已经检查过的常量，没有任何检查依赖比较结果。

**结果。** 9 个证明在一次普通的 `cargo kani` 里全部通过，跑法和 CI 相同，每个进程限制 14 GB 地址空间，连编译共 81 秒。
`defects_arrays` 是同样的树的数组形式，只在 `cfg(kani)` 下存在，为的是让这种形式也持续被证明，固件里没有它。

**诚实地说。** 这个证明这么容易，是因为剩下要证明的东西很少：下标全是常量、没有循环的程序根本没有越界的机会。这正是这种形式的意义，证明确认的是实际运行的代码。
它不说明数值对不对，那是输出范围和 `self_check` 的事。`outputs_batch` 不属于 `predict`，这些证明不覆盖它。
